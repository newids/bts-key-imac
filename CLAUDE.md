# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project goal

A macOS menu bar app that makes a MacBook appear to an iMac as a Bluetooth keyboard and pointing device, with nothing installed on the iMac (it is a managed machine). Priorities: (1) keyboard forwarding, (2) trackpad as mouse, (3) clear local/remote mode switching. Windows support is a secondary, analyzed-only concern.

The full analysis and design, including the chosen transport (Bluetooth Classic HID via IOBluetooth as plan A, proven on the target iMac by the KeyPad app; BLE HID over GATT as plan B and the Windows path), SDP record, GATT layout, report IDs, the trackpad performance design, module boundaries (`HIDCore` / `ClassicHIDTransport` / `BLETransport` / `InputCapture` / `App`), the mode-switch state machine, the Windows single-source verdict, and the validation spikes to run before implementation, lives in `docs/analysis-and-design.md`. Read it before touching code; it is the source of truth for report formats and state transitions. How the layers of a Bluetooth connection (pairing, baseband link, HID channels) relate to what the app does, and how a new iMac is told from a known one, is in `docs/bluetooth-link-model.md`.

## Commands

```bash
swift build                                   # build all targets
swift test                                    # run all unit tests (HIDCore + SDP record builder)
swift test --filter HIDCoreTests              # one test target
swift test --filter KeyboardReportTests/testStatePressAndReleaseProducesReports   # one test
./scripts/build-app.sh                        # release build -> build/BTSKey.app (signed with BTSKey Dev, else ad-hoc; renders build/AppIcon.icns via scripts/make-icon.swift)
./scripts/build-dmg.sh                        # build-app + drag-to-Applications DMG in build/ (SIGN_IDENTITY / NOTARY_PROFILE optional; see docs/distribution.md)
defaults delete kr.newid.btskey hasCompletedOnboarding   # make the first-run guide show again
open build/BTSKey.app                         # run the menu bar app
/usr/bin/log stream --level info --predicate 'subsystem == "btskey"' --style compact   # runtime logs; use /usr/bin/log because zsh has a builtin `log`
```

`build-app.sh` signs with the self-signed `BTSKey Dev` certificate when the login keychain has one (how to create it is in `docs/distribution.md`), so Accessibility / Input Monitoring grants survive rebuilds. Without it the app is ad-hoc signed and both grants must be given again in System Settings → Privacy & Security after each build. `SIGN_IDENTITY=... ./scripts/build-app.sh` uses a Developer ID for distribution.

Hardware tests are written down step by step, split into what the person does and what the program does, in `docs/test-scenarios.md`.

## Architecture

SwiftPM package, four targets with a strict dependency direction (`HIDCore` has no Apple framework imports beyond Foundation and holds almost all unit tests):

- `Sources/HIDCore` — report descriptor (single source of truth for byte layouts), `KeyboardState`/`KeyboardReport` (6KRO plus a trailing Apple vendor Fn/🌐 byte, 9 bytes), `CapsLockMapping` (Caps Lock sent as itself by default, or as the 🌐 byte, or as a ⌃Space tap) and `CapsLockPreferences` (the choice per host). **What switches 한/영 on the iMacs tested is the iMac's own modifier remap for this keyboard** (Modifier Keys → select this Mac → Caps Lock → 🌐 fn); the iMac treats the MacBook as a generic Bluetooth keyboard and drops the Apple Fn byte, and nothing sent from the MacBook alone worked (`docs/input-source-switching.md`), `MouseAccumulator`/`MouseReport` (Int16 deltas, fractional carry, never drops motion), `MacKeycodeMap` (kVK → HID usage), `HIDPFrame` (Bluetooth HID profile framing/parsing), `SessionStateMachine` (pure reducer for idle/connecting/local/remote/disconnected; every exit from remote emits `unlockCursor`, and `sendAllUp` too whenever the link is still up to carry it), the connection policies (`ReconnectPolicy`, `HostCuePolicy`, `RemoteResumePolicy`), host identification (`PairingLedger`, `HostFamiliarity`, `PairedDeviceRecord`, `BluetoothDeviceKind`), `HostLinkDropFilter`, `LinkLayerStatus` (baseband link up versus HID channels open, which System Settings does not tell apart) and `HUDPresentation`.
- `Sources/ClassicHIDTransport` — `HIDTransport` protocol plus the Bluetooth Classic implementation. It publishes the SDP HID record (`SDPRecordBuilder`, service class 0x1124, subclass 0xC0) **once per app lifetime** (remove + re-publish fails because bluetoothd keeps the PSMs registered; the publish is retried every second because the attempt right after the Bluetooth permission prompt fails). **Links are always opened outbound by this app**: host-opened L2CAP channels are refused at once, because IOBluetooth either never surfaces them to the process (idle) or surfaces channel objects that never deliver data (while an attempt is in flight), so the host times out after 3 s either way (**never register `IOBluetoothDevice.register(forConnectNotifications:)`, it pins this process' device objects to isConnected()==false and makes every channel open fail with a callback storm; channel-open notifications never fire, with or without a PSM filter**). **A link the host brings up is invisible to this process while it is up**: no notification, and `isConnected()` stays false even in a fresh process. The one signal is the disconnect notification when that link drops 16 to 19 s later, so the transport keeps a standing disconnect notification on the target (`watchTargetForHostLinks`), `HostLinkDropFilter` discards the drops of links the app itself released, and `SessionController` connects outbound 1 s after the cue (`transportHostCameIntoRange`). That is how wake-from-sleep and "Connect" on the iMac work; it takes about 25 s from the host's attempt. `connectionComplete` is trusted (`isConnected()` lags and stays false for some pairing records) and the control channel is opened 1.5 s after it (`linkSettleDelay`: opened at once, a freshly paired iMac left the encryption request unanswered and the link died after 5.5 s); the `isConnected()` guard remains only on the grace path, because opening on a link IOBluetooth does not consider up makes it wait synchronously on the main thread. If the ACL already exists and the host opens no channels within 1.5 s the transport drops the ACL and reconnects afresh (channels on a link this process did not establish are closed by IOBluetooth within milliseconds). It answers control-channel requests and writes `0xA1 | reportID | payload` on the interrupt channel. IOBluetooth objects only work from the main thread, so everything runs on main with async APIs; `send` hops to main and uses `writeAsync` with a heap buffer freed in `l2capChannelWriteComplete`. A disconnect notification that arrives before the current attempt's link is up belongs to the previous link and is ignored. After a failure, a user disconnect and on quit the baseband link is released with `closeConnection()` so neither side keeps showing "connected". Errors carry `isRetryable`; `SessionController` retries retryable ones with `ReconnectPolicy.unattended` (**one** retry after 4 s, then only "지금 다시 연결"), never retries `.hostClosed` (channels closed while the link was up: the host disconnected on purpose, HID 1.1.1 §5.3.4.6), and honours a host cue once per success or user request (`HostCuePolicy`). A 15 s connect watchdog lives in the transport. Evidence for all of this is in `docs/connection-audit.md` (seven audits).
- `Sources/InputCapture` — `InputThread` (a dedicated userInteractive thread with its own run loop; the tap and HID monitors live there because a stalled main thread would make macOS hold *all* system input until it disables the tap, which is exactly what a 9 s IOBluetooth wait did in 0.1.0), `EventTapCapture` (session-level CGEvent tap on that thread; passes everything through except the toggle hotkey when not capturing, swallows everything when capturing; pointer motion coalesced on an 8 ms timer, buttons flushed immediately; Caps Lock synthesized as press+release from flagsChanged; left/right modifiers distinguished via NX device bits so right-⌘ Korean toggle works), `CapsLockMonitor` (IOHIDManager on the Caps Lock usage: with "Caps Lock switches input source" a short tap never changes the Caps Lock flag, so the event tap alone cannot forward 한/영 taps), `InputSourceKeeper` (restores the MacBook's input source after remote mode), `CursorLock` (a background app cannot freeze or hide the pointer with the public calls, so the pointer is warped back on every swallowed motion event and hidden via the `SetsCursorInBackground` connection property), `Hotkey` (default ⌥⌘K), `InputPermissions`. The 8 ms mouse timer only runs in remote mode.
- `Sources/BTSKeyApp` — AppKit menu bar app. `StatusMenuController` composes the menu: `DeviceMenuSection` (known hosts from `Settings.knownHosts`, icon per `BluetoothDeviceKind`, other paired computers in a submenu), settings and help submenus, About. `OnboardingWindowController` hosts the SwiftUI `OnboardingView` (steps from `OnboardingStep` in HIDCore; `OnboardingModel` polls `AppPermission` status) and is shown on first launch or from Help; `show(at:)` opens it at one page, which is how the Caps Lock menu shows the input source setup. `SupportActions` holds the About panel, the `SMAppService` login item, and diagnostics export (app log + Bluetooth inventory to the Desktop). `AppInfo` holds version and support URLs. `PairedDeviceWatcher` polls the paired-device list every 5 s (macOS gives no notification). **The list is read by a helper process** (`PairedDeviceLister`, the app's own executable run with `--list-paired`): **never call `IOBluetoothDevice.pairedDevices()` in the app process, one call makes every later channel open fail with -536870212 and stalls main** (it returns a Mac paired over both transports as two objects). The list is folded into `PairingLedger`, which is stored in UserDefaults, so a pairing made while the app was not running is reported at the next launch; an empty list is treated as "daemon unavailable" and a removal must be seen twice, otherwise a bluetoothd hiccup wiped history and dropped the target. Every device is tracked, not only computers, because an iMac that started the pairing is stored with class of device 0; `BluetoothDeviceKind.isHostCandidate` then decides by `HostFamiliarity` (new / returning / repaired / untried / unpaired). A newly paired host becomes the target and is connected unless a link is in use (the standard "move to another iMac" flow), several at once are left to the user, and a forgotten pairing stops retries immediately. The watcher never pages a device: `remoteNameRequest` opened links to iMacs the user was not sitting at and collided with connection attempts, so a host without a name shows a placeholder until its first connection. At launch the saved intent is resumed only after the first list (`onFirstList`). Every `NSMenu` here sets `autoenablesItems = false`, otherwise AppKit re-enables items whose target responds to the action and `isEnabled` from `render()` is ignored. `SessionController` records every connected host into `Settings.knownHosts` and is the only place that mutates session state (it also re-enters remote mode via `RemoteResumePolicy` when a link that dropped during remote mode returns within 30 min, so an iMac waking to its login screen gets the keyboard back): it feeds `SessionEvent`s to the state machine and performs the returned `SessionEffect`s (transport, cursor lock, HUD). `StatusMenuController` renders the three-state icon and menu; `Settings` wraps UserDefaults; `HUDWindow` is the overlay for connection and mode changes (wording, tone and display time come from `HUDPresentation` in HIDCore; a gauge around the badge drains over the display time, the close button dismisses it, "connecting" stays until a result replaces it); `MainThreadWatch` logs main-thread stalls; `RemoteStatusOverlay` is the box pinned under the status item for the whole remote mode; `PowerSaver` dims the built-in display via private DisplayServices (resolved with dlsym) per `PowerSaveMode` and persists the brightness to restore after a crash.

Changing `ReportDescriptor` may need the iMac to forget and re-pair this Mac, because the host appears to cache the descriptor from pairing time.

Runtime prerequisites: the iMac must already be Bluetooth-paired (bonded) with this Mac, the app needs Accessibility + Input Monitoring, and KeyPad must not be running (it publishes a competing HID record on the same link).
